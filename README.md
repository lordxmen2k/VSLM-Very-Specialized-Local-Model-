# VSLM — a linear algebra model you can train on one 12 GB card

**Very Specialised Local Model.** A QLoRA fine-tune of `Qwen3-1.7B-Base` that
answers linear algebra questions, shows its working, and draws the figure.

Everything the model learns from is generated by this repository. There is no
scraped corpus, no borrowed dataset and no third-party model in the loop:
sympy computes every answer, so the training data is correct by construction
and reproducible from a seed.

This repository is meant to be read as much as run. Every design decision
below is explained with the reason it was made, and the mistakes the project
found along the way are written down rather than quietly fixed — see
[docs/HOW-IT-WORKS.md](docs/HOW-IT-WORKS.md).

## What you can learn from this

- **How to build a domain corpus** so that the ground truth cannot drift away
  from the question it answers, and how to check that it has not.
- **What a LoRA actually changes** — 2 % of the parameters, and a completely
  different behaviour.
- **How to use a benchmark's error taxonomy as a design document.** The
  benchmark told this project which algorithm to teach; the taxonomy said
  which failure it was trying to measure.
- **How to read a training log.** Tokens per second, allocated versus
  reserved memory, and what a step time that swings between eleven and
  thirty seconds is actually telling you.
- **How several real bugs hide.** Every one of them was invisible to the
  test that existed at the time, and all of them are written down.

## What it produces

The model is given a question and replies in four labelled blocks:

```
### Problem
For v = \begin{pmatrix} 3 \\ 5 \end{pmatrix} and w = \begin{pmatrix} 3 \\ 1 \end{pmatrix},
compute the orthogonal projection of the first vector onto the second, and the residual.

### Scratchpad
GIVEN: v = \begin{pmatrix} 3 \\ 5 \end{pmatrix}, w = \begin{pmatrix} 3 \\ 1 \end{pmatrix}
STEP 1 <v, w> = 14 and <w, w> = 10
STEP 2 proj = (<v,w> / <w,w>) w = \begin{pmatrix} \frac{21}{5} \\ \frac{7}{5} \end{pmatrix}
STEP 3 residual = v - proj = \begin{pmatrix} \frac{-6}{5} \\ \frac{18}{5} \end{pmatrix}
STEP 4 VERIFY proj + residual = v and proj is parallel to w. OK

### Answer
p = \begin{pmatrix} \frac{21}{5} \\ \frac{7}{5} \end{pmatrix}, r = \begin{pmatrix} \frac{-6}{5} \\ \frac{18}{5} \end{pmatrix}

### Plot
{"kind":"projection","data":{"vectors":[[0.6,1.0],[1.4,0.2]]},"labels":{"title":"projection of v onto w"},"annotate":["orthogonal projection"]}
```

Three consequences, and they are the whole point of the design:

**The scratchpad is computed, not written.** Every step in it is what sympy
actually did. The model learns the habit of computing and then checking,
because every derivation in the training data ends with a `VERIFY` line that
re-checks the result.

**The model never draws.** It emits a small declarative JSON object describing
the figure, and a deterministic renderer turns that into a PNG. Learning to
describe a picture is a far smaller competence than learning to draw one, and
it means the numbers in the picture are the numbers in the answer.

**The answer is checked, not trusted.** `la.answer` defines a restricted LaTeX
grammar for answers and parses it back into sympy. The evaluation harness
compares the model's parse against sympy's ground truth. Nothing about the
score depends on the model being right about itself.

## Quick start

Windows and Linux, on a card with 12 GB or more. Times below are measured on
an RTX 4070 SUPER.

```bash
git clone https://github.com/lordxmen2k/VSLM-Very-Specialized-Local-Model-
cd VSLM-Very-Specialized-Local-Model-

# Windows only - installs a CUDA-matched torch and bitsandbytes:
scripts\setup_windows_gpu.bat
# Linux:
#   pip install torch --index-url https://download.pytorch.org/whl/cu130
#   pip install --no-deps bitsandbytes==0.50.2
pip install -e ".[train,dev]"

make preflight     # 5 s   - check the GPU, the CUDA build and bitsandbytes
make data          # 1 min  - build 20,000 problems and a held-out set
make check-arithmetic  # 40 s - prove every printed derivation adds up
make speed-test    # 5-10 min  - measure the cost of a training step
make train         # ~75 min   - one epoch, measured
make eval          # score it on the held-out set
make bench-all     # score it against published frontier models
make chat          # ask it something
```

`make preflight` is worth running first and it is cheap: it catches the two
problems that cost the most time otherwise — a torch and bitsandbytes that do
not match, and a GPU that is already busy.

## The seventeen families

Every family is generated, verified by sympy, and paired with a figure.

| Family | What it asks | Figure |
|---|---|---|
| `determinant` | det of an n×n integer matrix | matrix heatmap |
| `solve_system` | solve Ax = b uniquely | A and its reduced row echelon form |
| `eigenvalues` | the spectrum, real or complex | eigenvalues on the complex plane |
| `diagonalize` | the diagonal form D in A = P D P⁻¹ | spectrum of D |
| `orthonormal_basis` | Gram–Schmidt to an orthonormal set | the basis in 2D or 3D |
| `projection` | projection of v onto span(w), and the residual | vector, projection, residual |
| `least_squares` | the least-squares solution of an overdetermined system | data and fitted line |
| `lu_factor` | L and U with LU = A | the upper triangular factor |
| `svd` | the singular values | singular value spectrum |
| `condition_number` | cond₂(A) | matrix heatmap |
| `rank_nullspace` | rank and nullity | a basis of the null space |
| `linear_transform` | T(v) and the image of the unit square | the unit square and its image |
| `matrix_trace` | tr(A) | matrix heatmap |
| `matrix_transpose` | Aᵀ | matrix heatmap |
| `matrix_multiply` | AB | matrix heatmap |
| `matrix_power` | Aᵏ | matrix heatmap |
| `matrix_vector` | Av | matrix heatmap |

The last five exist because they are operation types a published benchmark
uses. Without them a score on that benchmark would not be on the same axis as
anyone else's.

## Five decisions that shape everything

### 1. The ground truth is mechanical

There is no human-written answer anywhere in this repository. sympy computes
the answer, the scratchpad and the figure values, and the training data
inherits them. The usual failure of a domain corpus — the answer quietly
drifting away from the question it answers — cannot happen.

It also means the corpus is unlimited. The supply of training data is not a
constraint; the constraint is what one 12 GB card can get through in an
afternoon.

### 2. Every problem is asked several ways

A model trained on one phrasing of one shape of problem learns to recognise
that shape rather than to solve it. So each problem is asked three to five
ways (three to five templates per family), and the matrices are relabelled:
rows permuted, or put through a similarity transform, which preserves the
spectrum exactly. The answer is always recomputed from the matrix *as it
appears in the question*, so augmentation can never introduce an
inconsistency.

### 3. Above 3×3, the determinant is taught by elimination

This one comes from the benchmark, and the benchmark's own error taxonomy
says exactly why.

LinAlg-Bench classifies every failure into a taxonomy. For determinants,
eight of the sign-error subtypes are:

```
Product_Sign_Error   Operation_Direction   Rule_Interference
Parity_Sign_Error    Double_Negative_Trap   Alternating_Drift
Cofactor_Neglect     Silent_Sign_Flip
```

Two of them describe a failure that only a cofactor expansion can produce.

**`Alternating_Drift`** — "Model correctly applied (−1)^(1+j) for the first
few cofactors but then lost the +−+−+ checkerboard pattern... Or inside a
nested 4×4 minor expansion, loses the pattern midway."

**`Cofactor_Neglect`** — "The model computed the minor value correctly but
used it directly in the final assembly without applying the (−1)^(i+j) parity
factor. The parity step was simply skipped entirely."

A 5×5 cofactor expansion *is* a nested 4×4 minor expansion. Those two
subtypes are the failure mode of doing the 5×5 the obvious way.

Row addition leaves the determinant alone, and the only sign in the whole
procedure is the number of row interchanges — there is no alternating
pattern to lose. So above 3×3 the corpus teaches elimination, and the
scratchpad shows the eliminations and the diagonal product:

```
STEP 1 eliminate below each pivot by adding a multiple of one row to another,
       which leaves the determinant alone
  row 2 -= (-1) * row 1
  row 3 -= (4) * row 1
STEP 2 the upper triangular form has diagonal -1, -2, 18
STEP 3 det(A) = -1 * -2 * 18 = 36
```

5×5 is in the training mix on purpose. A corpus that had only ever seen 2×2
and 3×3 would be useless at exactly the size where the frontier models break.

**And at 3×3 the corpus teaches cofactors**, because the benchmark sometimes
asks for them explicitly. Of the fifty 3×3 determinant problems in
LinAlg-Bench, eighteen say *"Use cofactor expansion along the first row"*;
the 4×4 and 5×5 problems specify no method at all. The corpus teaches what
the benchmark asks for at each size: cofactors at 3×3, elimination above it.

This also puts a hard constraint on the corpus. The taxonomy judges models on
exactly the step this project once got wrong: the 3×3 expansion in the
training data printed the signed minors and left out the matrix element, so
the expression it wrote was not the determinant. A corpus that exhibits
`Cofactor_Neglect` would be teaching the error the benchmark measures.

### 4. Nothing in the training signal is a copy task

Two lines of every example used to be pure duplication, and both were
removed.

The `GIVEN` line reprinted the matrix that the question already contains.
It was 17 % of the supervised text spent transcribing. It now names the
objects and moves on:

```
GIVEN: A, b
STEP 1 det(A) = -48 != 0, so A is invertible and the solution is unique.
```

The orthonormalisation step printed the same matrix twice, identically, and
mislabelled the quantity it was printing — it computed the *squared* norm and
called it `||w||`. Both are fixed.

The corpus went from 781 to 672 characters per example. Fourteen per cent
less work, and a better signal: the model is never asked to copy.

### 5. Every derivation ends with a check

Each generated derivation closes with a `VERIFY` line. The model learns to
state the check, which is the one thing that separates a model you can audit
from a model that merely sounds certain.

This matters more than it looks, because a derivation that does not add up is
worse than no training at all. `make check-arithmetic` walks every family,
finds every line that states an expression and a result, evaluates the
expression with sympy and compares it with the result it claims. It caught a
real bug — the 3×3 cofactor expansion printed the signed minors and left out
the matrix element, so the line it wrote evaluated to 8 while claiming 4.
The ground truth was right, so no test comparing the answer with the truth
would ever have noticed.

## How it fits on a 12 GB card

`Qwen3-1.7B-Base` is 1.72B parameters: 28 layers, hidden size 2048, 16 query
heads, 8 KV heads, head dimension 128, tied embeddings, 32,768-token native
context.

| | |
|---|---|
| Weights, bf16 | 3.44 GB |
| Weights, NF4 (QLoRA) | ~0.9 GB |
| KV cache per token | 112 KB (bf16) · 56 KB (q8_0) |
| KV cache at 8K context | 0.88 GB (bf16) · 0.44 GB (q8_0) |

Inference is comfortable. Q4_K_M weights (1.1 GB) plus an 8K context plus
runtime overhead is about 2.2 GB; at 32K context in bf16 it is about 7.6 GB.
A 131K context fits only if the KV cache is quantised, and only just.

Training is the part that needs care, and QLoRA is what makes it work:

| Method | VRAM | Host RAM | Fits 12 GB? |
|---|---|---|---|
| Full fine-tune, AdamW | 27.5 GB | — | no |
| Full fine-tune, 8-bit Adam | 10.3 GB | ~6 GB | tight; no room for activations |
| Full fine-tune, offloaded optimiser | 6.9 GB | ~21 GB | yes |
| **LoRA, bf16 base** | **~7 GB** | ~2 GB | yes, comfortable |
| **QLoRA, NF4 base** | **~2 GB** | ~2 GB | yes, very comfortable |

The default is QLoRA: 4-bit NF4 with double quantisation, rank 32, alpha 64,
gradient checkpointing, sequence length 768, batch size 1 with 16 gradient
accumulation steps (an effective batch of 16), `paged_adamw_8bit`, bf16
compute, lr 1e-4 on a cosine schedule with 3 % warmup, one epoch.

Those numbers are measured, not chosen. `make speed-test` runs the same data
through five micro-batch shapes at the same effective batch of 16, each shape
in a process of its own:

```
   batch  accum  eff   s/step     tok/s    ex/s  alloc GB  resv GB   frag  free GB
       1     16   16     4.19     1,256     0.2     10.01    12.02   2.00     8.78
       2      8   16    24.08       218     0.1     16.09    22.42   6.33     8.78   OVER THE CARD
       4      4   16    out of memory
       8      2   16    out of memory
      16      1   16    out of memory
```

**One shape fits: batch 1.** A batch of two needs **16.09 GB of live
tensors** on a card with 12.88 GB, so it cannot run at 768 tokens however
much of the card is free. The reason is the vocabulary: the logits, the
fp32 copy the loss is computed in, the log-softmax and their gradients come
to about **6 GB per example** over 151,936 tokens. The model itself is under
1 GB — the output layer is the whole problem.

Batch 1 is also the *right* answer rather than merely the only one: at batch
1 a batch's width is that example's own length, so there is no padding
waste, and the peak is set by the longest example rather than by the cap.

**The corpus, measured.** 20,000 examples at a mean of 324 tokens, which is
6.5 M tokens per epoch. 1.0 % of them are longer than the 768-token cap and
are truncated — down from 2.9 % before the duplication was removed.

**The training budget.** The finished run measured **143 minutes** for 1,250
steps at 885 tokens per second, with the loss going from 1.3258 to 0.0462 and
a peak of 5.04 GB allocated. The speed test suggests less — it runs seven
steps on a card that has not warmed up, where a real run is two and a half
hours of sustained load. **Plan on the measured run, not the speed test.**

**The limit that matters is the allocated column**, not the reserved one.
That run reserved 13.35 GB on a 12.88 GB card and ran perfectly well, because
on Windows the driver maps host memory into the device address space and the
allocator counts it as reserved. Live tensors are the constraint: a batch of
two needs 16.09 GB of them, and there is nowhere for that to go.

Measuring this took four attempts and the first three were wrong. The speed
test ran all five shapes in one process, so the caching allocator carried
its fragmentation from one to the next. Fixing that, the parent process then
held a copy of the model on the GPU while its children measured, so every
row was taken against a card that was already partly full. Both are fixed;
the `free GB` column reports how much of the card was free when each row
began, and the shuffle is fixed so every shape draws the same examples. The
lesson is in [docs/HOW-IT-WORKS.md](docs/HOW-IT-WORKS.md): a number is not a
measurement until you know what else was running.

Only 1.99 % of the parameters are trainable: 34,865,152 LoRA parameters
against 1,755,440,128 in total. The frozen base is never updated.

**Measured.** On an RTX 4070 SUPER, at batch 1 with 16-way accumulation, a
training step takes **4.19 s** and the run holds **10.01 GB** allocated of the
card's 12.88 GB. That is 1,256 tokens per second.

Those numbers are why `make speed-test` exists. The reason a bigger batch
does not fit is memory, not arithmetic, and it is written up under
[When something goes wrong](#when-something-goes-wrong).

## Install

### Windows

```bat
scripts\setup_windows_gpu.bat
```

It installs a CUDA-matched torch and torchvision from the PyTorch index,
installs bitsandbytes with `--no-deps`, and restores the packages a previous
attempt may have bumped. See
[When something goes wrong](#when-something-goes-wrong) if you are doing this
by hand.

### Linux

Install torch **first**. If it is missing, `pip install -e ".[train,dev]"`
pulls it in from PyPI as a dependency of peft and accelerate, and PyPI's
torch is built against a CUDA release that an older bitsandbytes has no
binary for.

```bash
pip install torch --index-url https://download.pytorch.org/whl/cu130
pip install --no-deps bitsandbytes==0.50.2
pip install -e ".[train,dev]"
```

### Why torch is not in the requirements

The `train` extra deliberately lists **neither torch nor bitsandbytes**. Both
resolve from PyPI, and pip is then free to replace a working CUDA-matched
torch with one that breaks the run. Install those two yourself, from the index
that matches your GPU, and pip will leave them alone.

`make setup` therefore never touches torch. If torch is missing,
`make preflight` says so in one line.

## The commands

Every target works from any directory in the tree: `scripts/Makefile` forwards
to the root one, because make does not search upward for a makefile.

### Build the corpus

```bash
make data                       # 20,000 train + 200 held-out
# or
python -m la.build_dataset --n-train 20000 --n-test 200 --seed 7 --out data --workers 4
```

Writes `data/train.jsonl`, `data/test.jsonl` and a sample of rendered figures
in `data/figures/`. The build is deterministic: the same seed gives the same
corpus, whatever the worker count.

Measured: about **594 problems a second** on four workers, so the 20,000
problem training set takes about 34 seconds, and the 40 sample figures add
about half a minute at 0.77 s each.

### Render a sample of figures first

```bash
make sample
```

Cheap sanity check: 240 problems and 24 rendered figures, about a minute. Look
at `data-sample/figures/` before building the whole corpus.

### Check the corpus before you trust it

```bash
make check-arithmetic
```

```
checked 3400 problems across 17 families
every printed expression evaluates to the value it claims
```

### Measure what a training step costs

```bash
make speed-test
```

Runs the same data through five micro-batch shapes and reports the cost of
each, with the real token count of the corpus. Each shape is measured in a
process of its own, because the caching allocator does not give back memory
it has cached, and the parent holds no GPU memory while they run. The
`free GB` column is how much of the card was free when that row started; if
it is not the whole card, the row is not measuring what it claims to:

```
  corpus: 2000 examples, 648,588 tokens, mean 324 tokens, median 292, p95 588, max 1205
  sequence cap: 768 tokens
  TRUNCATED: 20/2000 examples (1.0%) are cut at the cap.
  card free at the start: 11.57 GB of 12.88 GB

   batch  accum  eff   s/step     tok/s    ex/s  alloc GB  resv GB   frag  free GB
       1     16   16     4.19     1,256     0.2     10.01    12.02   2.00     8.78
       2      8   16    24.08       218     0.1     16.09    22.42   6.33     8.78   OVER THE CARD
       4      4   16    out of memory
       8      2   16    out of memory
      16      1   16    out of memory
```

Read it one way or the other. If `s/step` is flat across the rows, the cost
is per token and the levers are fewer tokens or fewer examples, not a
different batch shape. If it falls steeply, the micro-batch shape was the
problem. A row marked `OVER THE CARD` has passed the card's physical memory
and is running over PCIe; the `frag` column shows how much of the reserved
memory is fragmentation rather than live data.

### Train

```bash
make train TRAIN_ARGS="--max-steps 20 --limit 200 --log-every 1"   # smoke test
make train                                                          # the real run
```

The smoke test is twenty steps on two hundred examples — about a minute — and
it tells you the step time, the peak VRAM, the time spent waiting for the
loader and the tokens per second. The real run prints the same thing every
twenty steps.

Useful flags:

| Flag | Effect |
|---|---|
| `--max-steps N` | stop after N optimiser steps |
| `--limit N` | use only the first N examples |
| `--epochs N` | passes over the corpus (default 1) |
| `--lr 1.5e-4` | learning rate |
| `--precision bf16` | LoRA on an unquantised bf16 base (~7 GB) instead of NF4 (~2 GB) |
| `--max-seq-len N` | cap the sequence length (default 512; the corpus runs to about 450) |
| `--rank N`, `--alpha N` | LoRA rank and alpha (default 32 and 64) |

### See what the model actually wrote

```bash
make explain
```

Reads the per-example results that `make eval` writes and says, for the
questions the model got wrong, whether it wrote a derivation at all. That
distinction is the one that matters after a training run: a model that emits
a derivation and gets the arithmetic wrong is a different problem from one
that jumps straight to the answer.

```
  of the failures, 128 wrote no scratchpad at all (64%)
  and 0 wrote no answer block (0%)
  the failures wrote a median of 0 STEP lines

family                 wrong  no scratchpad  median steps
  matrix_multiply          61              61             0
```

`python -m la.explain data/results.jsonl --family matrix_multiply --n 3`
shows the completions themselves.

### Measure the inference speed

```bash
python -m la.bench --perf --adapter runs/vslm
```

Time to first token, decode throughput at batch 1, 4 and 8, peak VRAM and
model load time.

## Reading the results

### The held-out set

```bash
make eval
```

```
  answer correct        142/200  (71.0%)
  plot kind correct     168/200  (84.0%)
  plot values correct   121/200  (60.5%)
  abstained              14/200  (7.0%)
```

followed by a per-family and per-difficulty breakdown.

**The abstention rate is not a footnote.** A model that always answers has a
100 % rate on the problems it guessed and 0 % on the ones it did not, and the
headline number cannot tell you which is which. A model that abstains
correctly on a fifth of the problems is more useful than one that confabulates
the same fraction.

### What the first trained model showed

The first full run — 1,250 steps, 153 minutes, loss 1.3465 → 0.0661 — scored
**46 %** on the held-out set, and the per-family breakdown was the finding:

| answer type | families | score |
|---|---|---|
| a scalar | eigenvalues, trace, transpose, rank_nullspace, svd | **100 %** |
| a scalar, sign-sensitive | determinant | 38 % |
| a matrix or a vector | condition_number, least_squares, lu_factor, multiply, power, vector, solve_system | **0–15 %** |

Every family whose answer is a matrix or a vector failed, and every scalar
family succeeded. That is the shape of the corpus, because **the corpus
stated results instead of deriving them**: a matrix product was written as

```
STEP 2 AB = egin{bmatrix} 4 & 0 & 2 & 16 \ ... \end{bmatrix}
```

with the sixteen dot products never shown. The model was being asked to emit
a sixteen-term sum in one forward pass. A model trained on derivations that
assert results learns to assert results.

Every derivation now shows its arithmetic, one line per dot product, and the
determinant's cofactor sign is written as its own factor so the alternating
pattern is copyable rather than computed. The same went into the six
families that are not benchmark tasks: `solve_system` now shows the
elimination and the back substitution instead of an inverse matrix,
`least_squares` shows AᵀA and Aᵀb, `lu_factor` shows the elimination,
`condition_number` shows AᵀA and its eigenvalues, `orthonormal_basis` shows
the unnormalised vectors and the rescaling, and `projection` shows the ratio
and each component.

The corpus went from 672 to 826 characters per example and the sequence cap
from 768 to 1,024 tokens, which takes an epoch from 2.5 hours to 3.2. The
full account is in [docs/HOW-IT-WORKS.md](docs/HOW-IT-WORKS.md).

### The published benchmark

> **Read the 4×4 column with care.** LinAlg-Bench's 4×4 questions are a bare
> matrix with **no instruction at all** — while the 3×3 and 5×5 questions say
> "Find the determinant of the 3×3 matrix A" and "Show all intermediate
> steps". Nothing tells the model what is being asked, so every model scores
> near zero there; the fine-tuned one and the base one both score exactly
> 0/220. That column measures the data, not the model. The report says so,
> and a test checks it against the real files.
>
> The fine-tuned model also scored **35.5 points below the base model at
> 3×3** — and the per-task breakdown shows the regression is entirely on the
> tasks whose derivations were expanded, while the one-line-answer tasks are
> flat. The held-out set, with our own phrasings, went the other way. That
> is a question-format distribution shift, and the raw completions are what
> will settle it. See
> [docs/HOW-IT-WORKS.md](docs/HOW-IT-WORKS.md#what-the-benchmark-said).


> **The grader was wrong before the model was.** Three separate bugs in the
> grading harness would have made correct answers score zero: the answer
> grammar had no rule for a bare comma-separated list, so all ninety
> eigenvalue problems failed to parse; the benchmark rounds its eigenvalues to
> four decimal places and the comparison used a tolerance of 1e-9; and
> `\boxed{...}` was extracted with a non-greedy regex that stopped at the
> brace inside `\begin{bmatrix}`, truncating 420 of the 660 answers. All
> three are fixed, and `tests/test_benchmark_grading.py` now downloads the
> real benchmark and checks that every reference parses, that a correct
> answer scores correct, and that a wrong answer scores wrong. See
> [docs/HOW-IT-WORKS.md](docs/HOW-IT-WORKS.md).

```bash
make bench              # LinAlg-Bench, with the published table printed
make bench-all          # the above, plus the base model as a baseline, plus --perf
```

| Llama-3.3-70B | 63.1 % | 60.6 % | 28.3 % |
| GPT-4o | 66.6 % | 36.0 % | 28.7 % |

Add `--baseline` and the base model is scored on the same problems, so the
delta attributable to the fine-tune is printed rather than asserted. That
comparison is the honest one: it holds the questions, the grader and the
hardware fixed, and changes only the weights.

The prompts are the benchmark's own, not ours. `la/benchprompt.py` reproduces
the system prompt, the preamble and the per-subcategory task statement. The
released 4x4 problems carry no task at all - the benchmark's pipeline reads a
column the released files do not have - so the task is reconstructed from the
subcategory label, and the report says how many problems that affected.

**What the table says.** The fall from 4×4 to 5×5 is where the models
separate: the strongest hold up (Gemini-3.1-Pro 94.6 % → 88.0 %, o1
92.3 % → 81.4 %) while the weaker ones fall off a cliff (Claude-4.5-Sonnet
69.7 % → 33.1 %, Mistral-Large 75.6 % → 45.1 %, Qwen2.5-72B
39.8 % → 24.6 %). The benchmark's error taxonomy says why the 5×5 column is
the hard one — for determinants it lists eight sign-error subtypes, and two
of them, `Alternating_Drift` and `Cofactor_Neglect`, describe a failure that
only a cofactor expansion can produce, including losing the ± pattern "inside
a nested 4×4 minor expansion", which is what a 5×5 cofactor expansion *is*.
That is the failure this corpus is aimed at.

**One thing to know about the LaTeX.** LinAlg-Bench writes every matrix as
`\begin{bmatrix}`. This corpus writes `\begin{bmatrix}` or `\begin{pmatrix}`,
chosen from the contents of the matrix, so the same matrix is written the same
way within an example while different matrices in the same example may use
different environments. The answer grammar accepts both. A model that has only
ever seen one spelling would meet the other for the first time on benchmark
day.

## When something goes wrong

### `make preflight` first

```bash
make preflight
```

Prints the Python and torch versions, the CUDA build, the GPU name and its
VRAM, whether 4-bit quantisation actually works on *this* machine, whether
the corpus is present, and what nvidia-smi says the GPU is doing right now.
It is the difference between a dozen lines and a thousand-line traceback.

### bitsandbytes will not load

`bitsandbytes` ships pre-compiled binaries for specific CUDA versions. The
current release, 0.50.2, bundles CUDA **11.8, 12.1, 12.4, 12.6, 12.8, 13.0
and 13.2**. The import **succeeds** even when the binary does not match, and
the failure arrives later, inside model loading:

```
RuntimeError: CUDA VERSION MISMATCH
Requested CUDA version:          13.2
Detected PyTorch CUDA version:   13.2
Available pre-compiled versions:
  - 11.8 ... 13.0
```

Three ways out, in order of least effort.

**Let the script handle it.** The training script probes bitsandbytes with a
real 4-bit quantisation on the GPU *before* it commits to the path. If the
probe fails it prints why, falls back to a LoRA on a bf16 base, and carries
on:

```
4-bit quantisation is unavailable: CUDA VERSION MISMATCH ...
falling back to a LoRA on a bf16 base. It fits in about 7 GB on a 12 GB card,
so the run proceeds; only the memory headroom is smaller.
```

**Upgrade bitsandbytes.** If yours is older than 0.50.2 it has no CUDA 13.2
binary, and this is the whole fix:

```bash
pip install -U bitsandbytes==0.50.2
```

`make preflight` prints the CUDA builds the installed bitsandbytes actually
ships, read out of the package directory, and compares them with your torch.
If it says `cuda match YES`, the problem is gone.

**Move torch down** to a CUDA version every bitsandbytes has. This is what
`scripts\setup_windows_gpu.bat` does:

```bash
pip install --index-url https://download.pytorch.org/whl/cu130 \
    torch==2.12.1+cu130 torchvision==0.27.1+cu130
pip install --no-deps bitsandbytes==0.50.2
```

Going this way has one advantage: torchvision 0.27.1 pins `torch==2.12.1`, so
it clears that conflict on the way past.

**Do not run `pip install --force-reinstall bitsandbytes`.** It reinstalls
every dependency at its newest version, which drags torch in from PyPI and
bumps `fsspec` and `filelock` past the versions `datasets` and `virtualenv`
accept. Use `-U` and `--no-deps`. If you have already run it, put the two
back:

```bash
pip install "fsspec[http]==2026.7.0" "filelock>=3.24.2,<4"
```

`constraints.txt` pins them for future installs.

One more thing worth checking: **Python 3.14 is very new** and the torch and
bitsandbytes wheel coverage for it is still catching up. If anything else
misbehaves once the CUDA issue is resolved, a 3.12 or 3.13 environment is the
safe choice.

### The training is slower than it should be

If the speed test reports an `alloc GB` figure larger than your card's
memory, the run is spilling into host memory over PCIe, and on Windows that
is several times slower than staying on the card. The measured table above
shows it exactly: batch 1 at 10.01 GB allocated runs at 1,256 tokens per
second, batch 2 at 16.09 GB runs at 218, on the same effective batch and the
same tokens.

The lever is the micro-batch, and the reason is the vocabulary rather than
the model. The logits dominate the memory — a bf16 copy, the fp32 copy the
loss is computed in, the log-softmax, and the gradients of all of it, over
151,936 tokens — and they cost about **6 GB per example** at 768 tokens. The
base weights are under 1 GB. The output layer is the whole problem, and it is
why a batch of two needs 16 GB of live tensors on a card with 12.9.

Halving the micro-batch halves that term, which is the only reason batch 1
runs at all.

**Look at `alloc`, not `resv`.** A finished run reserved 13.35 GB on a
12.88 GB card and ran perfectly well: on Windows the driver maps host memory
into the device address space, and the caching allocator counts that as
reserved. It is the live tensors that have to fit on the card.

`make speed-test` prints `OVER THE CARD` next to any row whose *allocated*
figure crosses the limit, and the header reports how many examples the
sequence cap is cutting and how much of the card was free when the run began.

### "triton not found; flop counting will not work for triton kernels"

Harmless, and silenced by this project. It is a logging warning that PyTorch
emits at import time of `torch.utils.flop_counter` on any CUDA build without
triton, which is the normal case on Windows — the official triton wheels are
for Linux and macOS.

The counter it guards, `FlopCounterMode`, is a diagnostic that sums
shape-based FLOP formulas. This project never uses it, and PyTorch's own
documentation for it says the workload still executes normally. Nothing about
training, inference or the benchmark score depends on it.

`la/__init__.py` sets the level on that one logger, so the warning is gone
and every other warning still shows. Installing `triton-windows` would also
silence it and change nothing else; there is no reason to.

### The step times swing

A training step that takes 11 seconds one time and 32 seconds the next, with
no trend, is not a slow GPU. It is the GPU being interrupted.

Windows time-slices the GPU between processes through the display driver. A
browser with a video playing, a video call, a container runtime or an
overlay all hold a context on the card, and the scheduler will hand them a
slice in the middle of your training step. The interruption length is not
predictable, which is exactly what the variance looks like.

`make preflight` asks nvidia-smi what the GPU is doing and warns if it is
more than 5 % busy. Close the browsers, the video call and the container
runtime before a long run, and watch the step times settle.

One counter is not comparable across platforms. PyTorch's caching allocator
reports *reserved* memory, and on Windows the driver can map host memory into
the device address space, so the reserved figure can exceed the card's
dedicated VRAM. The *allocated* figure is the one to watch: 7.8 GB of 12.9 GB
is comfortable.

### `make: *** No rule to make target 'preflight'`

You are in a subdirectory. Make does not search upward for a makefile.
`cd ..` fixes it, and `scripts/Makefile` forwards every target so that it
keeps working from anywhere.

### A make override does nothing

`make train TRAIN_ARGS="--epochs 2"` used to be silently discarded, because
the recipe never referenced `$(TRAIN_ARGS)`. It works now. If you override
something and nothing changes, check `make -n train` first — and note that
the defaults are not on the command line, so the training script prints its
own resolved configuration when it starts.

## Limits and honest caveats

- **Scope.** Introductory through applied numerical linear algebra. Functional
  analysis and infinite-dimensional theory are out. If you widen it, widen the
  families to match.
- **The graded answer is the mathematics.** For `orthonormal_basis` a basis is
  only determined up to the sign of each vector, and for `diagonalize` up to
  the order of the diagonal entries, so those two are compared with the
  corresponding tolerance rather than exactly.
- **A plot is not a proof.** The harness compares the numbers in the plot
  against the numbers in the reference, not the pixels. That is deliberate: it
  tests the mathematics, and a rendering difference should not be able to
  fail a correct answer.
- **The scratchpad is a training target, not a guarantee.** The model will
  sometimes write arithmetic that does not check out. The host-side verifier
  is what makes that visible.
- **The timings in this README are measurements, and only from one machine.**
  The training step cost was measured on an RTX 4070 SUPER with the GPU
  shared with other applications. On an idle card it will be faster. No claim
  in this file is an estimate dressed up as a measurement; where a number is
  unknown it says so.
- **Copyright.** This repository generates its own data and downloads nothing
  except the benchmark. If you extend it with human-written textbooks, check
  the licence before you redistribute the resulting weights.
