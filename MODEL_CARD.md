# Model card — VSLM

**Very Specialised Local Model.** A QLoRA fine-tune of `Qwen3-1.7B`
that answers linear algebra questions, shows its working, and draws the
figure.

This card states what the model does, what it does not, and how both were
measured. Every number here was produced by the code in this repository and
can be reproduced from a seed.

---

## Model details

| | |
|---|---|
| Base model | `Qwen/Qwen3-1.7B` (the instruction-tuned checkpoint) |
| Method | QLoRA — 4-bit NF4 base, bf16 LoRA adapters |
| Trainable parameters | about 2 per cent of the base |
| Licence | Apache-2.0 |
| Hardware used | one NVIDIA RTX 4070 SUPER, 12,282 MiB |
| Training time | 146 minutes for 1,250 optimiser steps |
| Peak allocated memory | 6.41 GB |
| Final training loss | 0.031 |
| Corpus | 20,000 problems, generated by this repository |
| LinAlg-Bench | **41.7%** (275/660) — base model 46.4% |

## Intended use

- A study of how a domain corpus is built so that the ground truth cannot
  drift away from the question it answers, and how to check that it has not.
- A teaching aid. The model shows the algorithm and draws the figure, so a
  learner can see the method rather than a bare number.
- A reproducible harness for fine-tuning on one consumer graphics card.

## Out of scope

- **It is not a general mathematician.** It is taught seventeen task
  families. Outside them it reverts to base-model behaviour.
- **It is not a calculator.** sympy does the arithmetic. The model chooses
  and explains the algorithm.
- **It does not verify its own answers.** The corpus checks every answer
  at build time. At inference the model will sometimes produce a wrong
  number and will say it is right.
- **It is not a frontier model.** The published benchmark scores ten
  frontier models between 24 and 94 per cent. A 1.7B model trained on
  20,000 synthetic problems is not in that class and should not be
  presented as if it were.
- **It is not yet better than its base model.** Run 5 scores 41.7 per cent
  against the base model's 46.4. The gap is an answer-contract mismatch in
  two families, not a capability gap, and the fixes are specified in
  [WORKING_STATE.md](WORKING_STATE.md#run-5-result--the-benchmark-ran-correctly-and-exposed-three-corpus-bugs).

## Training data

Everything the model learns from is generated here. sympy computes every
answer, so the ground truth is correct by construction and reproducible from
a seed. No scraped corpus, no borrowed dataset, no third-party model in the
loop.

Seventeen families: determinant, solve_system, eigenvalues, diagonalize,
orthonormal_basis, projection, least_squares, lu_factor, svd,
condition_number, rank_nullspace, linear_transform, matrix_trace,
matrix_transpose, matrix_multiply, matrix_power, matrix_vector.

Each problem is asked three to five ways and its matrix relabelled, because
knowledge memorised without paraphrase and permutation is not extractable at
all — Allen-Zhu and Li report zero per cent accuracy for knowledge learned
that way.

The determinant is taught two ways on purpose: cofactor expansion up to
3x3, elimination above it. The benchmark's error taxonomy says models fail
at 5x5 because they are locked into cofactor expansion and lose the sign, so
the algorithm that does not collapse is the one taught.

**Every answer in the corpus can be read back by the grader.** Measured over
6,000 generated examples: all 6,000 truths parse, and a model that reproduces
an answer exactly is scored correct in all seventeen families. That property
is what makes the held-out score mean something — it was not true until the
grammar was fixed, and while it was false, 28 per cent of the orthonormalisation
answers were scored wrong with the model having them exactly right.

## Evaluation

There are two measurements and they are not the same thing.

### 1. In-distribution held-out set — 54.5 per cent

200 problems, unseen instances, generated by the same seventeen families
with a different seed and the family order reversed.

**This measures generalisation within the taught families.** It does not
measure linear algebra. A model that had learned the seventeen templates
and nothing else could score well on it.

### 2. LinAlg-Bench — independent

660 problems from a third-party benchmark, with different wordings, a
different generator and nine operation types. This is the only measurement
in the project that does not depend on the training data.

| | 3x3 | 4x4 | 5x5 | overall |
|---|---|---|---|---|
| **This model** | 52.7% | 43.6% | 28.6% | **41.7%** (275/660) |
| `Qwen/Qwen3-1.7B`, no adapter | 75.0% | 41.8% | 22.3% | 46.4% (306/660) |
| OpenAI-o1 | 94.6% | 92.3% | 81.4% | — |
| GPT-4o | 66.6% | 36.0% | 28.7% | — |

**This model currently scores below its own base model.** The fine-tune
beats base on 4x4 (+1.8 points) and 5x5 (+6.4 points) and loses badly on
3x3 (-22.3 points). That inversion is not a capability gradient; it is an
answer-contract mismatch, and it is diagnosed below. The fixes are
specified in [WORKING_STATE.md](WORKING_STATE.md#run-5-result--the-benchmark-ran-correctly-and-exposed-three-corpus-bugs).

By task, the fine-tuned model and the base model score:

| task | fine-tuned | base |
|---|---|---|
| transpose | 60/60 (100.0%) | 49/60 (81.7%) |
| trace | 56/60 (93.3%) | 58/60 (96.7%) |
| matrix_vector | 45/60 (75.0%) | 44/60 (73.3%) |
| matrix_power | 43/60 (71.7%) | 34/60 (56.7%) |
| multiplication | 33/60 (55.0%) | 25/60 (41.7%) |
| rank | 21/60 (35.0%) | 21/60 (35.0%) |
| nullity | 15/60 (25.0%) | 19/60 (31.7%) |
| eigenvalue | 1/90 (1.1%) | 2/90 (2.2%) |
| determinant | 1/150 (0.7%) | 54/150 (36.0%) |

Three verified causes for the two collapsed families:

1. **Rank and nullity are taught as a pair.** The corpus's single
   `rank_nullspace` family answers `rank = 2, nullity = 1`. The benchmark
   asks for rank *or* nullity and grades against the scalar `2` or `1`.
   The grader reads the last number out of the pair, so it sees the
   nullity and never the rank — asked for the rank, the model is wrong
   every time, with the right number sitting where the grader cannot see it.
2. **Eigenvalues are taught as exact values.** Every one of the 90
   generated corpus eigenvalues is an exact number — 86 integers and 4
   exact complex pairs, not one irrational. The benchmark's 90 eigenvalue
   questions all need irrational decimals, and the model has never been
   shown a value it has to round.
3. **The 3x3 determinant is taught by cofactor expansion**, which is the
   exact method the benchmark's error taxonomy says models fail at.

**The grader has been checked against the real benchmark, and it is now
checkable without a GPU.** All 660 reference answers parse, a model that
answers correctly scores 660/660 in every shape it might write the answer in,
and a wrong answer scores wrong. Getting there took four bugs in the grading
harness, three of which would have made correct answers score zero — and one
of which rejected 28 per cent of the orthonormalisation answers even when the
model had them exactly right. The account is in
[docs/HOW-IT-WORKS.md](docs/HOW-IT-WORKS.md#bugs-this-project-found).

**The base model knows more than it scores.** Read leniently, from
anywhere in its response, it reaches 76.4% on 3x3 against 75.0% scored
strictly on `\boxed{}`; but 128 of its 660 answers never produce a
parseable value at all, and it runs to the token cap on most problems
(95.3 minutes for the base pass against 35.9 for the adapter). The
fine-tune's advantage is reliable, well-formed, stoppable output, and
that is not yet reflected in the score.

### Why a fine-tune can score below its own base model

Run 1 scored 17.0 per cent while the base scored 29.5. Run 5 scores 41.7
while the base scores 46.4. Both times, the cause was not mathematics.

**Run 1 — the prompt did not match.** The corpus asked the questions in
one format and the benchmark asked them in another, so the model answered a
prompt it had never seen and wrote prose the grader could not read. Fixing
the prompt took the held-out set from 45.0 to 54.5 per cent and the
unreadable answers from 23 in 200 to none.

**Run 5 — the answer shape did not match.** The prompt now matches. What
does not match is the *answer contract*: the benchmark asks for rank or
nullity separately and the corpus answers both; the benchmark asks for
irrational eigenvalues and the corpus answers exact integers; the
benchmark's 3x3 determinant is a method the corpus teaches in the one form
the benchmark says fails.

That gap is the most useful thing this project has to say about itself: a
fine-tuned model is not better than its base model until it is scored the
way it was trained, **and until the shape of its answer matches the shape
being asked for**. The per-task table is the map of that contract — when a
fine-tune loses to its base, read it before touching the model.

## Limitations

- Narrow. Seventeen families and a fixed output format.
- **Two families are broken against the benchmark** — determinant (0.7%)
  and eigenvalue (1.1%) — because the corpus teaches the wrong answer
  shape for the benchmark's questions. This is the largest known
  limitation and it is a corpus defect, not a model defect.
- The derivation is not guaranteed. Every corpus derivation ends with a
  verification step, and the model reproduces the *form* of a verification
  step without necessarily performing it.
- Formatting is load-bearing. A model that answers correctly in a
  different format scores zero. The grading is deliberately lenient about
  the last boxed answer and strict about the arithmetic — but a format the
  grammar cannot read at all still scores zero, and that has happened twice
  in this project's history. Both times the answer was right and the check
  was wrong. Run 5 shows the same failure one layer down: the *grader* is
  right and the *corpus* taught the wrong shape.
- 4x4 and 5x5 determinants are the weakest area, and they are the area the
  benchmark weights most heavily.

## Performance

Measured on the RTX 4070 SUPER, bf16, batch 8:

| | |
|---|---|
| Peak VRAM allocated | 9.62 GB |
| Batch 1 | 402 tokens in 13.14 s = 30.6 tok/s |
| Batch 4 | 4,096 tokens in 33.27 s = 123.1 tok/s |
| Batch 8 | 8,192 tokens in 41.71 s = 196.4 tok/s |
| Full 660-problem benchmark, adapter | 35.9 minutes |
| Full 660-problem benchmark, base | 95.3 minutes |

The base model's pass is 2.7x slower because it does not stop: it runs to
the token cap on most problems. The adapter's advantage is reliability of
termination, not raw speed.

The decode step is **CPU-dispatch-bound, not GPU-bound**: ~11,229 torch
op events per step at 401 per layer, of which only 1,812 are
`cudaLaunchKernel`. Measured CPU issue time is ~34.4 ms against a GPU
drain time of ~1.3 ms, so the GPU is idle about 98.6% of the step. The
realistic ceiling on this hardware without `torch.compile` is roughly
1.2-1.5x, and `torch.compile` needs Triton, which has no official Windows
wheel. Attention is 0.64 ms of a 38 ms step — 2 per cent — so installing
FlashAttention would change nothing.

## Reproducing

```
make setup            # install
make setup-gpu        # install the CUDA-matched torch (Windows)
make check            # tests, arithmetic check, a small corpus
make data             # build the corpus
make train            # 146 minutes on one 4070 SUPER
make eval             # the in-distribution held-out set
make bench            # LinAlg-Bench, the independent measurement
```

The corpus is a deterministic function of its seed, so `make data` twice
produces byte-identical files.
